# Sandbox

> A functional design workspace for features, interaction experiments, prototypes, utilities, viewer/player behavior, and other explorations of how things work.

The sandbox is both a **human development space** and an **agent-readable workspace**. It exists to make functional experimentation cheap: ideas can be tried, changed, broken, rebuilt, documented, and revisited without needing to become promoted features or portfolio entries first.

## Sandbox and Work serve different purposes

**Sandbox is for functional design.** It is where features and experiments are built, tested, and iterated. An item may remain a demo or prototype indefinitely; it does not need to be a finished portfolio project.

**Work is a visual sampler and overview.** The `/all/` page represents created work across its underlying categories. A piece can be small—a logo, photograph, or other discrete visual result—and still merit inclusion when it is developed enough to stand on its own. Inclusion means it has been snapshotted as a recognized piece of work, with the possibility of future iteration; it does not mean it is permanently final.

The distinction is not simply unfinished versus finished. Sandbox explores what something can do; Work records what has been created. Some work may inform both, but the two spaces should not be forced into one-to-one parity. See [`https://github.com/joeldom/redesign/blob/gh-pages/all/ALL_WORK.md`](https://github.com/joeldom/redesign/blob/gh-pages/all/ALL_WORK.md) for the separate rules governing the Work catalog.

## How to use it

### For humans

- Experiment first; organize when organization becomes useful.
- Keep unfinished work. A rough experiment can become a feature, a project, a reference, or nothing at all.
- Prefer small, reversible changes while exploring.
- Reuse existing site infrastructure when it helps, especially the shared style guide and established CSS variables/utilities.
- Document an experiment when its purpose, behavior, or setup would otherwise be easy to lose.

### For agents

Before changing anything:

1. Inspect the existing sandbox item and its surrounding files.
2. Preserve unrelated work and existing comments/structure unless a change requires otherwise.
3. Prefer the smallest useful change over a broad refactor.
4. Reuse existing site/style-guide resources instead of introducing duplicate systems.
5. Test the rendered result when working on HTML/CSS/JS.
6. Keep experiments independently understandable where practical.
7. Update documentation or viewer metadata when a change affects how an item is opened or understood.

Do not assume every sandbox item needs to be production-ready, generalized, framework-based, or cleaned up. The sandbox is explicitly allowed to be strange, redundant, temporary, visual, technical, or unfinished.

## From Sandbox Demo to Promoted Feature

A demo in the sandbox is not automatically a site feature. Keep it available as a working experiment until a deliberate snapshot captures the version being considered for promotion. That snapshot is a reviewable milestone: it lets the feature be promoted from a sandbox demo into a proper site feature without erasing the experiment's history or assuming that every future refinement belongs in the demo.

KUMO / 雲血 is the current example. Since KUMO has been integrated into the top of the site, pause further KUMO development by default. Reopen it only when a specific refinement is needed; make that refinement in a clearly versioned iteration, and keep the existing sandbox implementation as the demo/reference until a deliberate snapshot is made for promotion. Apply the same lifecycle to Viewer and the player/UXBG work: the existing sandbox versions remain useful demos until a snapshot is chosen for promotion to a proper feature.

Promotion is a deliberate decision, not an automatic consequence of a prototype becoming useful. Before promotion, compare the candidate snapshot with the current main and portable implementations, document the intended behavior, and verify the integration paths.

## Future-state concepts

These are recorded ideas, not active builds. Keep them here until there is time to prototype them; do not treat their inclusion as a commitment to a release date. The concepts could eventually become standalone pages linked from the portfolio or sandbox.

### 1. Door Index — a link portal with a random door

A page that collects as many useful links as practical, with a recognizable *Resident Evil 1*-style door sprite as the central interaction. Activating the door randomly selects and opens one destination from the curated link set.

- **Purpose:** Turn a dense link index into a small, memorable discovery interaction rather than a conventional directory.
- **Core behavior:** Maintain a clear list of destinations; choose one at random when the door is activated; make the destination understandable and ensure the interaction remains usable with keyboard and assistive technology.
- **Visual direction:** Use the visual language of classic RE1 door-transition sprites as inspiration. Confirm appropriate sprite assets and usage before implementation rather than assuming assets are already available.
- **Design consideration:** Randomness should feel playful, not obstructive. Keep a conventional way to browse or inspect the links so visitors are not forced to rely on chance.

### 2. Influence Library — a Steam-like reference grid

A compact, tightly packed tile grid for browsing influences, references, and inspirations. The presentation should evoke the density and scannability of a Steam library, adapted to a visual/design reference collection rather than a game launcher.

- **Content:** Influences and references across defined categories; each tile should lead to more context where useful.
- **Layout:** Dense, consistent tiles with enough visual material to recognize each reference quickly.
- **Filtering:** Category filters update the visible collection without losing the overall sense of a unified library.
- **Motion:** Tiles animate into view when the page loads and when a filter changes, using a restrained white-or-black reveal/transition that works against the current theme.
- **Design consideration:** Keep filtering and motion fast, readable, and accessible; support reduced-motion preferences and avoid animation that delays access to the content.

### 3. Masks — a 5 × 4 design-ethos grid

A page containing **20 masks**, arranged five columns wide by four rows high at the intended desktop layout. Each mask represents a different design ethos, visual mode, or style the work tends to draw upon.

- **Content:** Each mask should explain a distinct approach or sensibility, not merely name a color palette. The collection can describe recurring design instincts, influences, and modes of expression.
- **Presentation:** Treat each tile as a recognizable identity with its own visual character, while keeping the overall grid cohesive.
- **Interaction:** Selecting a mask can reveal its explanation and examples of where that ethos appears in the work.
- **Responsive behavior:** Preserve the 20-item collection while allowing the grid to reflow naturally on narrower screens; five-by-four describes the target desktop composition, not a requirement to squeeze mobile.
- **Open question for a later pass:** Define the 20 mask identities and whether the masks are presented as archetypes, selectable modes, or descriptive labels for existing work.

These three ideas have different jobs: the **Door Index** is playful navigation, the **Influence Library** is a searchable reference archive, and **Masks** is a self-portrait of the design approaches behind the work. They should remain distinct even if they eventually share styling or components.

## Viewer direction

The sandbox is intended to grow into a viewer-driven workspace rather than simply a directory of links.

A sandbox item can eventually declare how it should be opened:

```js
{
  id: "example",
  title: "Example Experiment",
  path: "./example/",
  type: "html",
  viewer: {
    type: "iframe",
    mode: "fullscreen"
  }
}
```

Possible viewer types include:

- `iframe` — isolated live HTML/CSS/JS experiments.
- `document` — Markdown or other readable documents.
- `code` — source/code inspection.
- `media` — image, video, audio, or other media.
- `page` — a normal sandbox page.
- `custom` — specialized viewer behavior when an experiment needs it.

The default live-code direction is an iframe so an experiment's CSS and JavaScript can remain isolated from the sandbox shell. Where sandboxing is appropriate, use restrictive iframe permissions such as `sandbox="allow-scripts"` rather than granting capabilities automatically.

The sandbox's descriptions are intentionally broader than the portfolio's project catalog. An item may be an experiment, visual study, support utility, prototype, or unfinished idea without being a finished portfolio project. When work is explicitly represented on the `/all/` page, use [`all/ALL_WORK.md`](https://github.com/joeldom/redesign/blob/gh-pages/all/ALL_WORK.md) for the separate catalog rules: page-order tracking, verbatim source transcription, confirmed details, and reconciliation with `all/index.html`.

The eventual viewer can provide responsive layouts such as a full viewport, mobile presentation, padded presentation, or a large-screen central viewer with surrounding context. The current direction is roughly a 20% / 60% / 20% composition on large screens, with the central 60% acting like a narrow, devtools-like experiment viewport.

## Markdown is a first-class sandbox format

Markdown files should be viewable through the same viewer system. A rendered Markdown document can use the site's existing typography, spacing, colors, CSS variables, and other style-guide primitives instead of becoming a separate visual system.

This makes Markdown useful for:

- experiment notes
- design studies
- technical documentation
- agent instructions
- specifications
- source material
- temporary planning documents

## Style guide

Sandbox experiments should be able to consume the shared site's style language when useful. The goal is not to force every experiment into the same visual treatment, but to make the style guide available as a common foundation for typography, spacing, color, responsive behavior, components, and viewer UI.

An experiment may intentionally depart from the style guide when the experiment itself is testing a different visual or interaction direction.

## Repository model

The current active workspace is `joeldom/redesign/sandbox` because it is also where experiments can be featured directly on the portfolio site.

A separate [`joeldom/sandbox`](https://github.com/joeldom/sandbox) repository is intended for deeper or more autonomous agent work as the sandbox grows. Moving an experiment there should be treated as an organizational decision, not a requirement for every experiment.

High commit activity in `redesign` is acceptable while the sandbox is actively being developed and maintained as a solo-contributor workspace. There is no need to create branches solely to make the repository history look quieter.

## Experiment lifecycle

A useful path is:

```text
idea
  ↓
experiment
  ↓
live preview
  ↓
viewer
  ↓
style-guide / UX testing
  ↓
feature or project
```

There is no requirement that an experiment graduate. Keeping something in the sandbox is a valid outcome.
